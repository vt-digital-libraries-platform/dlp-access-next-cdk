# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

Two independent npm projects, each with its own `package.json` and `node_modules`:

- **Root**: Next.js 16 / React 19 app (App Router, Tailwind 4). Deployed to Elastic Beanstalk (`.elasticbeanstalk/`, `.platform/`, PR-preview workflows in `.github/workflows/`).
- **`infra/`**: CDK v2 (TypeScript). Each environment gets three stacks. `DlpAccessNext-<env>-Data` holds the DynamoDB tables and the OpenSearch domain. `DlpAccessNext-<env>-Api` holds the AppSync API, the Lambda that streams table changes to OpenSearch, and the environment's Elastic Beanstalk instance role. `DlpAccessNext-<env>-Auth` holds the environment's Cognito user pool, or points at an existing one. Each git branch of the Next.js app can get a `DlpAccessNext-Web-<branch>` stack, an Elastic Beanstalk application and environment that uses one environment's API. The Amplify apps still run separately with their own data. The spec is `docs/issues/multi-env-data-layer.md`.

## Commands

Root: `npm run dev`, `npm run build`, `npm run lint`, `npx tsc --noEmit`. The root app has no test suite.

CDK: run everything from `infra/`, or `--app is required` is raised.

```bash
cd infra
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
npx cdk synth  --all -c env=dev -c account=$ACCOUNT
npm run deploy -- -c env=dev -c account=$ACCOUNT                                                                  # confirms, then cdk deploy --all
npm run deploy -- -c env=dev -c account=$ACCOUNT -c branch=$(git branch --show-current)                          # Web stack on the existing dev stacks
npm run deploy -- -c env=f-search -c account=$ACCOUNT -c branch=$(git branch --show-current) -c backend=provision # also deploys f-search's Data and Api
npm test                 # Jest: assertions on each environment's synthesized templates
npm run test:lambda      # pytest: streaming handler (one-time setup: python3 -m venv .venv && .venv/bin/pip install -r lambda/requirements-dev.txt)
```

- `env` is required. Allowed values are `dev`, `pre-production`, `production`, or `f-<slug>` for a feature environment, which uses dev's settings except for data protection. Names are lowercase and at most 20 characters, because the domain is `dlpnext-<env>` and OpenSearch allows 28. Per-environment settings (region, removal policy) and the two sizing profiles live in `infra/lib/environments.ts`.
- `account` is required: the 12-digit AWS account ID to deploy to. No account IDs are stored in the repo. `production` belongs in a separate account from the others.
- `production` is an optional boolean (`-c production=true`, default false) that picks the sizing, independently of `env`: false gives one `t3.small.search` node and a `t3.small` Beanstalk instance; true gives three `m7g.medium.search` nodes across three AZs and a `t3.medium` instance. `-c env=production` without it gets the small sizing.
- Only feature environments (`f-<slug>`) delete their data when their stacks are destroyed. `dev`, `pre-production` and `production` keep their tables and domain, and turn on table deletion protection and PITR.
- `-c userPool=<user pool ID>` makes the environment use an existing Cognito user pool, which must be in the environment's region; without it the Auth stack provisions a new pool (`dlpnext-<env>`, admin-created users who sign in by email, an `admin` group, and the managed login domain `dlpnext-<env>-<account>`). It only applies when the environment's stacks are in the app (no `-c branch`, or `-c backend=provision`). An existing pool is not changed by the Auth stack: it needs its own managed login domain and `admin` group. Dropping `-c userPool` on a later deploy switches the environment to a new pool, so keep passing it.
- `-c identityProvider=<name>` names the federated identity provider on the user pool that users sign in through (`VT-SSO-OIDC` on the existing VT pool); without it users are the pool's own (`COGNITO`). It applies where `-c userPool` does and must likewise be passed on every environment deploy. CDK only records the name: the provider must already exist on the pool when a Web stack deploys, or creating its app client fails. On a new pool that means adding it by hand after the Auth stack deploys, so `-c backend=provision` in one run can't work with a new pool and a federated provider.
- `-c appUrl=<https origin>` (with `-c branch`) is the app's public origin. It is added to the branch's Cognito app client as a callback and sign-out URL and set as `APP_BASE_URL`. Cognito rejects `http` callbacks other than localhost, and the Beanstalk environments serve only HTTP, so without HTTPS in front of the app and this option, sign-in works only for the app running on `localhost:3000`.
- `-c branch` adds a Web stack. The branch name is slugified (`whunter/Multi_Env` becomes `whunter-multi-env`); the Beanstalk application and environment are named `dlpnext-<slug>`, so the slug can be at most 32 characters. With `-c backend=attach` (the default), the app contains only the Web stack, and the environment's Api and Auth stacks must already be deployed; otherwise the deploy fails with "Unable to fetch parameters". With `-c backend=provision`, the app also contains the environment's Data, Api and Auth stacks, and the Web stack deploys after them. Deploying the same branch with a different `env` repoints its existing Web stack.
- `npm run deploy` (`infra/bin/deploy.ts`) validates the options with the app's own `planApp`, prints them and the stacks (`describePlan` in `infra/lib/deploy.ts`), with a bold red banner above them when `env` is `production` (`productionWarning`, which also flags a missing `-c production=true`), and runs `cdk deploy --all <same args>` only on `y`/`yes` (any case). Anything else, or closed stdin, exits 1 without deploying. The CDK app itself can't prompt, because the CLI runs it with stdin closed, and `npx cdk deploy` bypasses the confirmation.
- Deploys are user-run (the auto-mode classifier blocks Claude from running them); hand the user the command to run with `!`. The confirmation prompt needs a terminal, so the user runs it.

The Next.js server needs `APPSYNC_API_URL` set to the Api stack's `GraphQLApiUrl` output; the Web stack sets it for you. Beanstalk environments made outside CDK (the PR-preview workflow's `dev-env-sc` template, `eb deploy`) must set it themselves and use the `EbInstanceProfileName` output (`dlp-access-next-<env>-eb`) as their instance profile.

## Architecture

- **Schema is the source of truth**: `infra/schema/schema.graphql`. It is read-only (Query only, no Mutation/Subscription), and Archive/Collection are searchable through `fulltextArchives`, `fulltextCollections` and `searchObjects` (returns `[CatalogItem]`).
- **Resolvers are generated code strings**: `infra/lib/resolvers.ts` has generators (`getByIdCode`, `listScanCode`, `queryByIndexCode`, `hasOneCode`, `hasManyCode`, `openSearchQueryCode`) that emit APPSYNC_JS 1.0.0 source. `infra/lib/api-stack.ts` wires them to data sources. The model list, list-query names and GSIs are in `infra/lib/models.ts` (`MODELS`, `LIST_QUERY_FIELD`, `GLOBAL_INDEXES`), which the Data stack also uses to create the tables. Adding a model means updating the schema and `models.ts`.
- **Tables and search copy the vtdlpdev Amplify resources**. Tables are named `<Model>-dlpnext-<env>`, with hash key `id`, the same GSIs and `NEW_AND_OLD_IMAGES` streams. The streaming handler (`infra/lambda/opensearch-streaming/`, Amplify's Python function) names the index after the table name's first `-` segment, lowercased, so table names must start with `<Model>-`. Only Archive and Collection are streamed. An index-template custom resource per index (`dlpnext-archive`, `dlpnext-collection`) sets `auto_expand_replicas: 0-1` and the mappings that `infra/lib/search-mappings.ts` generates from the schema's `Archive` and `Collection` types, the same way the Amplify app does (`amplify/data/opensearch-mappings.ts` in dlp-access): strings are `text` with a `.keyword` subfield, `AWSJSON` is a `dynamic: true` object whose subfields are mapped as documents arrive, with `date_detection` off (a document whose value for the field is a bare string rather than a map is rejected), except `archiveOptions`, an object with explicit subfield mappings, and the `DATE_FIELDS` plus any `AWSDateTime`/`AWSDate` field are dates that accept several formats including `strict_date_optional_time`, with `ignore_malformed`. Mappings are `dynamic: false`, so attributes not in the schema stay in `_source` but are not indexed. The one field not from the schema is `date_range` (type `date_range`): the streaming handler derives it (`date_range.py`) as the interval from `start_date` to `end_date`, or one interval per `date` value when neither parses, widening each value to its precision (`1963` is the whole year, `194X` the decade) and dropping approximate markers. A document whose start is after its end gets no `date_range`. The search filter inputs take `date_range` with `gte`/`lte`, which match documents whose interval overlaps; sorting by date uses `start_date`. Templates apply only when an index is created, so an existing index keeps its old mappings until it is deleted and reindexed.
- **Streaming failures**: the handler re-raises errors (Amplify's version swallowed them). The event source mapping then retries 3 times, bisects the batch, and sends records that still fail to the `OpenSearchStreamingFailureQueueUrl` SQS queue. Rows written before the Api stack existed are never indexed (the stream starts at `LATEST`).
- **Web stacks find their environment by name, not by cross-stack reference**, so they can attach to stacks deployed from another CDK app run. The instance profile is `dlp-access-next-<env>-eb`, the Api stack writes the API URL to the SSM parameter `/dlp-access-next/<env>/graphql-api-url`, and the Auth stack writes the user pool ID to `/dlp-access-next/<env>/user-pool-id` and the identity provider name to `/dlp-access-next/<env>/identity-provider`; CloudFormation resolves the parameters at deploy time. The names come from `infra/lib/environments.ts`. The source bundle is the repo root minus `.gitignore` entries, `infra`, docs and `.env*` (see `BUNDLE_EXCLUDES` in `infra/lib/web-stack.ts`), and the Node.js 24 platform's prebuild hook (`.platform/hooks/prebuild`) builds it. `SOLUTION_STACK` pins the platform version; managed updates apply minor versions in place. Environments are single-instance, with no load balancer or custom domain.
- **User sign-in is Cognito**. Each Web stack creates its own confidential app client (authorization code flow, `openid email` scopes) on the environment's user pool, allowing only the environment's identity provider, and sets `COGNITO_ISSUER`, `COGNITO_CLIENT_ID`, `COGNITO_CLIENT_SECRET` and `COGNITO_IDENTITY_PROVIDER` on its Beanstalk environment. `/auth/login` passes the provider as `identity_provider`, so users go straight to it without managed login's chooser. Signing out ends the Cognito session but not the federated provider's, so the next sign-in may not prompt. `src/lib/auth.ts` and the `src/app/auth/` routes run the flow with `openid-client`; the session is the ID token in an httpOnly cookie, verified against the pool's keys on each request. `/examples/appsync-queries` and its server action require the `admin` group (`cognito:groups` claim). The client always allows `http://localhost:3000`, so a branch can be run locally with the Web stack's `CognitoIssuer`, `CognitoClientId` and `CognitoIdentityProvider` outputs; the secret comes from `aws cognito-idp describe-user-pool-client`.
- **API auth is IAM only**. Each environment's own Elastic Beanstalk instance role (`dlp-access-next-<env>-eb`) is granted `appsync:GraphQL`. The OpenSearch domain has no resource policy, so access comes only from the IAM grants on the roles that need it. The Next.js side signs requests with SigV4 in `src/lib/appsync.ts` (`aws4fetch` plus the Node credential chain), so it must only run server-side.
- **Demo page**: `src/app/examples/appsync-queries/` runs every query in the schema. The `list*` results seed the arguments for the `get*`, `*ByIdentifier` and search queries. Empty tables produce "skipped" entries instead of failures.

## AppSync JS runtime gotchas

- Variables cannot be reassigned (`let x = ...; x = ...` fails). Deploy validation reports only "The code contains one or more errors", so build values with a single `const` expression.
- `util.transform.toElasticsearchQueryDSL` returns a JSON *string*; wrap it in `JSON.parse`.
- Results typed as an interface (`CatalogItem`) need `__typename` set on each item. A Collection is identified by `collection_category`, otherwise it is an Archive.
- OpenSearch paging uses `search_after` sorted on `<field>.keyword`, except for the fields the generated mappings type as `date` or `boolean`, which are sorted on the field itself with numeric page tokens (`numericSortFields` in `openSearchQueryCode`). Total hits cap at 10000, as in Amplify.
